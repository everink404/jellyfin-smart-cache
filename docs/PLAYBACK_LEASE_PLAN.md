## 已确认的问题与接口证据

当前PrefetchHost.Select在协商时取得CacheLease，retained按媒体ID合并，释放发生在宿主停止。真实MCP日志证明一个选集过程会协商多项缓存；这些保护项不必然都实际播放。当前实现保证保守占用，不适合长期预算回收。

证据使用项目已固定的官方源码ee91c75e777da41a9c4f4855e70adc604fbf2ef8，沿用本机源码夹具，不依赖未核实的新版本接口：

- MediaBrowser.Controller/MediaEncoding/ITranscodeManager.cs：GetTranscodingJob(playSessionId)可查询作业；没有向插件公开统一的“所有读取结束”事件。
- MediaBrowser.Controller/MediaEncoding/TranscodingJob.cs：有PlaySessionId、MediaSource、Process、HasExited。这些能辅助跟踪转码，不等于覆盖所有文件读取者。
- MediaBrowser.MediaEncoding/Transcoding/TranscodeManager.cs：OnTranscodeEndRequest只减少ActiveRequestCount并启动计时，不意味着ffmpeg立刻退出；OnFfMpegProcessExited才设置HasExited。
- Jellyfin.Api/Helpers/StreamingHelpers.cs：可复用现有作业的MediaSource，未必每次重新走包装路由。一个HTTP响应结束也不意味着后台作业放弃输入路径。
- 当前RoutingManager的Select接口没有完整HTTP请求和PlaySessionId上下文。只把retained改为按会话字典不能补齐解析到实际打开间的保护。

## 候选生命周期

| 阶段 | 所需保护 | 释放门槛 |
|---|---|---|
| 纯PlaybackInfo预协商 | 先判断是否能使此阶段只报告可用性，实际取流再取得租约 | 必须验证所有客户端随后重解析，未证明前继续保守保护 |
| 实际文件响应／Range | 在决定返回缓存路径前取得请求租约 | 响应读取完成或中断，且确实不再由该响应引用；新Range请求重新取得租约 |
| 转码／重封装 | 从选源到ffmpeg取得输入的过渡租约，转交给明确作业 | 作业终止且相关读取结束；不能仅用播放停止、HTTP分片结束或定时器到期 |
| 字幕／附件提取 | 单独覆盖提取进程或其等待任务 | 提取任务结束，不能随播放器停止提前释放 |
| 同缓存多客户端 | 每个实际读取者单独持有，按缓存ID汇总引用数 | 所有引用均归零且无过渡请求，才进入可淘汰集合 |
| 不明来源或无法关联的路径 | 保持现有保守租约 | 服务退出；可观察地报告原因，不根据超时猜测安全 |

不采用单纯固定TTL释放。客户端可能在较长暂停、拖动或网络恢复后才请求；TTL不能证明路径已不再使用。也不凭GetTranscodingJob返回null就释放，因为作业创建前存在间隙，直放本身也没有转码作业。

## 实施顺序与通过条件

1. 先补齐复制诊断和占用观测；记录保护由哪一阶段产生，区分解析次数与实际播放数。
2. 本机在固定官方接口上验证请求上下文、响应生命周期、作业创建与结束关联，重点检查任何装饰器带来的DI循环；仍保留原保守策略作为无法关联时的回退。
3. 先覆盖纯协商未播放、直接Range响应、转码与字幕任务的不同读取者，验证租约转交无空窗；读取异常与取消也必须归还对应引用。
4. 再覆盖多客户端同集、旧会话迟到停止、切集、seek重新创建作业、连接中断和插件停用。容量压力下持续读取的缓存不得被删除，停止后无读取者的项最终可回收。
5. 在真实容器取得上述关键生命周期证据，才能替代“保护至重启”的行为。若12.1公共接入点不能覆盖全部读取者，明确缩小可释放范围，保留不明读取者的保护，不宣称全路径自动释放。

本方案不引入外部Worker，不改媒体库路径或条目。它说明后续技术调查与测试门槛，不代表已完成占用释放实现或真实验收。

## 本地观测候选（2026-10-15）

新增ReadObservation与按受管媒体ID汇总的ProtectionObservation。路由通过IHttpContextAccessor读取当前请求的控制器类别、是否Range、是否有唯一且格式有效的PlaySessionId；不保存HttpContext、原始查询、播放会话ID或认证资料。仅视频／HLS控制器请求尝试只读查询ITranscodeManager.GetTranscodingJob；纯预协商、字幕与后台调用不为诊断主动解析转码管理器。对无ID、多个ID或不符合GUID格式的ID保持未知，不能把未知当作安全。

查询到作业后还要匹配其MediaSource.Path与选定缓存路径；分别记录尚未观测到作业、输入不匹配、匹配但未退出、匹配且已退出。仅观察这次解析时点，没有持续追踪所有作业；不声称能覆盖没有再次调用路由的复用作业。读取线程之外的完整响应／任务完成仍未验证。

诊断服务查询在宿主缓存状态锁之外执行，异常只转为observation-unavailable，不能使新诊断故障阻断原有选源。保护记录不超过原有1000项租约上限，管理员API只返回最多50项；宿主关闭时同租约一起清理。配置页与选源日志能查看观测事实，仍明确标记保护至重启。

验证使用真实ASP.NET DefaultHttpContext／HttpContextAccessor、固定官方类型TranscodingJob以及只读管理器替身，覆盖Range关联、作业退出、相同会话输入不同、查无作业、无效／重复ID、后台未知、预协商不解析管理器、诊断异常隔离、私密数据不导出与异步上下文隔离。它不是实际HTTP响应完成、ffmpeg生命周期或真实容器的释放验收。旧通用测试代理不允许返回null，首轮查无作业检查因此失败；新增允许null的专用替身后重测，而非修改产品把异常当作查无作业。

下一步应先用真实HTTP响应执行验证静态文件的打开／完成／中断边界，并验证转码作业创建与请求租约转交；然后才能选择性开启安全释放。当前本地候选没有调用Dispose释放任何在用租约，没有TTL淘汰，也没有将HasExited作为全部读取结束的证据。

## 真实本机 HTTP 实验（2026-10-15）

`scripts/check-single-plugin.ps1 -HttpRead`新增显式启用的回环实验：Kestrel仅监听127.0.0.1随机端口，使用项目生成的32MiB测试源和单文件容量预算，不接触NAS。HttpClient禁用代理。启动后使用MVC PhysicalFileResult执行真实HTTP文件响应，EnableRangeProcessing=true，与固定官方FileStreamResponseHelpers.GetStaticFileResult相同；脚本额外核对该官方文件SHA-256 DD9F2A2EB73B1DB562D9FF4E70B4CCD94AA79B92ED48086266D7C26ECD034E89。没有编译执行整个Jellyfin辅助类或控制器。

夹具在选择缓存路径前取得CacheStore租约，用await ExecuteResultAsync覆盖真实执行，在finally归还。验证内容包括：

- 选择路径后、物理文件执行器打开前已有占用；此时容量压力无法淘汰。
- HTTP200完整内容、206 Range精确内容、416无效Range、HEAD只返回长度，结束后租约均归零。
- 打开前客户端取消能退出等待并归还；真实传输开始后，停止读取的客户端使发送阻塞且租约仍在，断开连接后执行栈退出并归还。
- 两个并发Range请求各自持有租约；首个结束后仍有一个引用，容量压力不能淘汰第二个请求的来源，第二个收到完整指定字节后引用归零。
- 所有请求结束后，新文件可以在同一小预算内通过LRU回收旧缓存。

初始受限执行没有完成回环连接；禁用代理后取得连接异常，允许本机回环连接的执行环境中通过。未把连接失败登记为产品读取故障。测试服务器在finally停止，临时测试文件留在.tools/http-read-checks以便复查。

这证明“请求级租约包住实际物理文件执行器”的静态读取方案在当前Windows/.NET10本机成立。它不证明生产插件已接入该方案，也不覆盖Jellyfin中间件安装次序、反向代理、Linux sendfile、ffmpeg／字幕进程或请求之间的作业转交。生产插件仍使用保护至重启策略；下一步在插件管线中验证请求作用域的注册与传递，并独立覆盖后台作业，不能把本次静态响应finally释放照搬到HLS或字幕任务。

## 请求作用域与后台交接候选（2026-10-15）

新增ReadLeaseStartupFilter、ReadLeaseMiddleware、ReadLeaseScope和BackgroundReadLeases。候选启动过滤器只在真实本机HTTP夹具注册；插件ServiceRegistrator未注册该过滤器，PrefetchHost仍使用原retained保护。不能把候选类存在写为线上或插件实际读取已经切换。

作用域通过HttpContext.Features传递，在await下游执行的外层using中关闭，finally恢复原feature。真实HTTP夹具改用该候选中间件，不再由端点自行Dispose；原文件读取、Range、HEAD、416、中断、双请求测试继续通过，新增端点抛异常后的清理检查。证明当前测试宿主的过滤器安装能覆盖端点执行和异常展开；尚未运行完整Jellyfin应用管线。

请求内同一文件只持有一个引用，最多16项。后台交接并非先归还请求引用再转移：在请求仍活跃时，为明确后台作业对象先取得第二个引用；两方随后各自结束，任何一方先结束都不会解除另一方的保护。后台记录以对象引用身份关联，不能拿相同文本PlaySessionId当作相同作业，避免旧作业迟到结束误释放替代作业。

后台注册最多128个作业、每作业最多16项；关联失败返回false，不丢弃请求已有保护。未来调用者必须在false时拒绝启动未受保护的后台读取或转为现有保守保护；不能忽略失败后继续使用路径。请求关闭后拒绝新取得与迟到交接。ReleaseAfterWork要求调用者已等待同一个作业结束；目前没有实现官方ffmpeg／字幕进程监视器，不能仅凭方法名推定能够自动识别作业结束。

验证新增13项所有权检查：请求去重、身份冲突、双引用交接、后台去重、关闭后拒绝取得／交接、相同值但不同对象的作业独立、无关或迟到停止、重复归还、后台先结束及注册容量限制。真实HTTP实验增至26项，其中后台任务在HTTP作用域结束之后才打开并读取缓存；中间容量压力被阻塞，读取完成并等待任务结束后才显式归还后台引用，最后可以LRU回收。

该后台读取为实际本机异步文件任务，不是ffmpeg或完整Jellyfin转码。累计229项C#检查通过（规划36、存储44、执行器32、读取39、宿主26、请求观测13、所有权13、HTTP26）。下一步应为真实转码／字幕任务取得同样的“启动前关联、结束后归还”证据，再决定哪些接入点可启用有限释放；仍未满足未知读取者自动释放门槛。
